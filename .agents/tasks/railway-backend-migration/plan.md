# Implementation Plan

## Grounded decisions

- **Service architecture:** add an independent `backend/` Node.js 22 + TypeScript service using **Fastify 5.6.2**, **Postgres.js 3.4.7**, and **Zod 4.1.12**. Fastify keeps the API small while providing maintained CORS, rate-limit, and multipart plugins; Postgres.js gives explicit SQL and transaction control without coupling Railway PostgreSQL to an ORM. The backend will have its own exact-version `package.json`, lockfile, TypeScript config, install/build/test/migrate/start scripts, and Railway health endpoint; it will not run through Vite.
- **Security dependencies:** use **argon2 0.44.0** for Argon2id password hashing, Node `crypto.randomBytes` for opaque session tokens, and SHA-256 only to hash those already-random tokens before storage. Pin `@fastify/cors` 11.1.0, `@fastify/rate-limit` 10.3.0, and `@fastify/multipart` 9.3.0 exactly; pin backend development tools as well.
- **Cross-origin auth transport:** return an opaque, high-entropy bearer token once at login, retain it in browser `sessionStorage`, and send it in `Authorization: Bearer` headers. This works reliably from a Vercel origin to a Railway origin without third-party-cookie restrictions and avoids cookie CSRF; the documented tradeoff is that any successful same-origin XSS could read the token, mitigated by short expiry, server-side revocation, no token logging, strict input/rendering practices, and clearing storage on failed verification/logout. No admin secret or credential goes in a `VITE_*` variable.
- **CMS model:** retain the existing atomic, revisioned `site_content` JSONB document because every current admin section edits one typed `SiteContent` snapshot and relies on optimistic revision matching. Validate the complete shape server-side with Zod; keep normalized financial/auth/assets tables separate. Replace Supabase Realtime with lightweight polling plus focus/visibility refresh so public tabs still receive published updates without introducing a second protocol.
- **Durable assets:** store uploaded bytes in PostgreSQL `bytea`, not Railway's ephemeral filesystem. Enforce the existing 10 MB limit and exact MIME allowlist (`image/jpeg`, `image/png`, `image/webp`, `image/gif`, `application/pdf`) on both client and server, sanitize metadata, and serve immutable absolute URLs under `PUBLIC_API_URL` so the Vercel frontend can render them.
- **Credential bootstrap/rotation:** on API startup, require Railway-only `ADMIN_USERNAME` and `ADMIN_PASSWORD`, upsert the single environment-managed admin with an Argon2id hash, and invalidate prior sessions when the username or password changes. Never print, return, or persist plaintext credentials; changing Railway secrets and redeploying rotates credentials.
- **Payment boundary:** migrate the existing donation ledger and webhook-event schema and expose only the authenticated donation-report read operation currently used by the dashboard. Do not add order creation, webhook acceptance, paid-status mutation, receipts, or a gateway adapter until a real provider and signature contract exist.
- **Package manager/verification:** use the repository's pinned pnpm 10.34.3 for the Vite app and an independent npm lockfile for the Railway service. Remove the stale root npm lockfile when removing Supabase so the root has one canonical lockfile. There is no existing test suite, so add only focused backend Node tests for validation/auth/error behavior and validate both production builds; do not start either long-running server.

## PostgreSQL migration/table inventory

- `schema_migrations`: records each applied migration checksum/version so Railway deploys are repeatable and fail safely on changed history.
- `admins`: UUID, normalized unique username, Argon2id password hash, active/environment-managed flags, credential version, and timestamps; replaces Supabase Auth plus `admin_users` for the one required administrator.
- `admin_sessions`: hashed opaque token, admin FK, credential version, created/last-seen/expiry/revocation timestamps; indexed for token lookup and expiry cleanup.
- `site_content`: singleton `main` row, schema version 2, validated JSONB covering announcement, page banners, home/about/story/focus/impact, fundraising campaigns, news, donation settings, public documents/reports, and contact settings; includes publish state, revision, timestamps, and updating admin.
- `site_content_revisions`: immutable content snapshots keyed by site/revision with changed-at/admin metadata; populated in the same transaction as optimistic content updates.
- `cms_assets`: UUID, original/safe filename, MIME, byte size, SHA-256 digest, `bytea` data, uploader FK, and timestamps; constraints enforce allowed MIME and 10 MB maximum, with digest/uploader indexes.
- `donations`: translated current provider IDs, donor fields, amount in minor INR units, campaign/purpose, status, receipt fields, provider payload, and paid/created/updated timestamps, retaining uniqueness and positive-amount/status constraints.
- `payment_webhook_events`: translated idempotency key, event type/payload, receive/process/error timestamps, unique by provider/event ID; retained for future trusted integration but not exposed to public writes.
- `admin_audit_log`: append-only action/resource/request metadata for login, logout, content writes, uploads, and protected financial reads; excludes credentials, bearer tokens, file bytes, and donor payloads.
- `monthly_donation_reports` and `yearly_donation_reports`: read-only aggregate views over verified paid donations, retained for reporting readiness.
- Migrations: `001_initial_schema.sql` creates extensions/tables/constraints/indexes/triggers/views; `002_seed_site_content.sql` inserts the complete current bundled schema-v2 defaults only when the singleton is absent. A local-only idempotent legacy importer translates exported Supabase `site_content`, revisions, donations, webhook events, and downloaded Storage objects, rewrites asset URLs, and deliberately replaces Supabase admin identity with the Railway-secret bootstrap account. The existing `supabase/migrations/202609290001_initial_backend.sql` remains unchanged and is clearly labeled historical in documentation.

## Assumptions and constraints

- No live Supabase credentials or export are present in the repository, so schema/default migration and an idempotent offline importer are implemented now; operators run the importer only if production Supabase contains content/assets/ledger rows beyond the bundled defaults.
- The existing repository has no test suite and is not currently a Git worktree (`git status` reports no `.git` directory). Implementation must work directly in `c:\Samriddhi-help-them-foundation`, create no worktree/branch/commit, never push, and rely on build/focused checks plus the documented Railway smoke test.
- Existing `public/documents/*` files and their relative CMS URLs remain valid Vercel static assets and must be preserved byte-for-byte. Only newly uploaded or explicitly imported legacy media is served from Railway's PostgreSQL-backed asset endpoint.
